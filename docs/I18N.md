# I18N.md — English + Romanian UI

Goal: every app switchable between RO and EN, with the choice shared
across all pages.

## Current state

| File | default `lang` | i18n system |
|---|---|---|
| `voice.html` | `ro` | ✅ working, attribute-aware |
| `editor.html` | `ro` | ✅ working, attribute-aware |
| `index.html` | `ro` | ✅ working, attribute-aware |
| `recipes.html` | `ro` | ✅ working, attribute-aware |

All five apps now share one `I18N`/`t()`/`applyUILang()` pattern and one
UI-language preference (`scula:ui-lang`, see below). The toggle lives in
the shared nav (`#navLangBtn`) rather than being reimplemented per app.

## The pattern (all five files)

Four moving parts — read `voice.html`'s "1. i18n" and "6. UI language"
script sections for the reference copy (`editor.html` and
`index.html` carry the same shape):

```js
const I18N = {
  ro: { settings:"Setări", copy:"Copiază", … },
  en: { settings:"Settings", copy:"Copy",  … },
};
let UI = "ro";
function t(k,a){                     // values may be functions
  const v = I18N[UI][k];
  return typeof v === "function" ? v(a) : v;
}
function applyUILang(){
  document.documentElement.lang = UI;
  document.querySelectorAll("[data-i]").forEach(el =>
    { el.textContent = t(el.getAttribute("data-i")); });
  const UI_ATTRS = ["placeholder","title","aria-label","value","alt"];
  UI_ATTRS.forEach(attr => {
    const d = "data-i-" + attr.replace("aria-label","aria");
    document.querySelectorAll(`[${d}]`).forEach(el =>
      el.setAttribute(attr, t(el.getAttribute(d))));
  });
  …
}
```

Markup carries keys: `<button data-i="settings">Setări</button>` and,
for attributes, `<input data-i-placeholder="searchHint">`. The literal
text/attribute in markup is always the RO fallback if JS fails.

**Values can be functions** — use that for pluralisation and
interpolation rather than string concatenation:
```js
ro: { count: n => `${n} cuvinte` },
en: { count: n => `${n} word${n===1?'':'s'}` },
```
A function key only ever takes **one** argument `a` (per `t(k,a)`); pass
an array/object and destructure inside the function if you need more
than one value (see `tooSmallForExport:([w,h])=>…` in `editor.html`).

`applyUILang` is attribute-aware in all five files now (the `data-i-*`
loop above) — this was the gap that used to force a tail of manual
fixups (`ta.placeholder = …` etc.) per file; don't reintroduce that,
add a new `data-i-*` attribute instead.

## ⚠ Do not conflate the two language axes in `voice.html`

- `S.ui` / `UI` → **interface** language. Toggle lives in the shared nav
  (`#navLangBtn`), see below.
- `S.lang` → **spoken** language for dictation, `ro-RO`/`en-US`/auto
  (L1268 area). Also has an "auto" value the UI language must never have.

They are independent: a user may want an English interface while
dictating Romanian. Never wire one to the other.

## Shared preference across pages — how it's wired

```js
const LANG_KEY = 'scula:ui-lang';   // 'ro' | 'en'
```

The toggle button (`#navLangBtn`) lives inside the shared `#site-nav`
block, so it's byte-identical in all five files (CLAUDE.md rule 2). Its own script only does two things:
1. paints itself from `localStorage[LANG_KEY]` (fast, synchronous, no
   dependency on the app script that hasn't run yet at that point in the
   page), and
2. on click, flips `localStorage[LANG_KEY]` and dispatches a
   `window` `CustomEvent("scula-ui-lang", { detail: lang })`.

**The shared block carries its own two-language table.** `ScuLaFolder`
(the save-destination button next to the toggle, plus its chooser sheet —
see `docs/FEATURES.md` § D) ships in the same shared block, which
runs *before* any app's `I18N` exists, so it can't use `t()`. It has a
small private `T = { ro:{…}, en:{…} }` and a `tx(k)` reading the same
`lang` variable, and repaints on both its own toggle click and the
`"scula-ui-lang"` event. Strings that belong to that block go in `T`, not
in an app's `I18N` — and they must be added to all five files
identically.

That includes every "saved to…" / "downloaded…" message: `save()` returns
an already-translated `r.message` and the app just prints it. Don't
re-add per-app copies of those strings — one wording, every page.

Each app's own script (loaded later, at the bottom of the page) is the
one actually holding `I18N`/`UI`/`t()`/`applyUILang()`. It:
- listens for `"scula-ui-lang"` and calls its own `applyUILang()` when it
  fires;
- on load, awaits its `store.get(LANG_KEY)` (the async wrapper with a
  `window.storage` → `localStorage` → memory fallback — see
  `voice.html`'s "3. Settings store" section) as the **source of
  truth**, falling back to `"ro"` if unset;
- `voice.html` additionally keeps writing `S.ui` inside its legacy
  `caiet-vocal:settings` blob for back-compat, but `LANG_KEY` wins on
  read.

Because `applyUILang()` runs inside an `async` IIFE at the very top of
each app's script (before any `let`/`const` declared further down the
file), keep that function free of references to state declared later in
the file — it's called once synchronously-after-`await`, before the
rest of the script has necessarily finished defining everything. Stick
to the generic `data-i`/`data-i-*` loop plus things you know exist at
parse time (the nav button, `localStorage`).

Set `<html lang>` on every switch — it drives hyphenation, spellcheck,
and screen-reader voice selection. Don't touch the `<html lang="en">`
inside `index.html`'s exported-HTML template string (~L7468)
— that's a separate, intentionally-English, self-contained document
shipped to people without the app (see `docs/MAP.md`).

## Known limitation: mid-session language switches don't repaint open modals

`applyUILang()` deliberately does **not** recompute already-rendered
dynamic content (an open "New canvas" / "Save all sizes" modal summary,
the layer list, an open image-explorer tree) — those functions are
declared with `let`s further down each file and calling them from the
early `applyUILang()` call risks a temporal-dead-zone crash. In
practice this is a non-issue: everything dynamic is generated fresh
(already in the current `UI`) the next time it's opened/re-rendered. If
you add a modal that stays open across a language switch, refresh it
explicitly from its own toggle handler — don't reach for it from
`applyUILang()`.

`index.html`'s idea box is the small worked example of that rule: its
hint line is generated (`ideaPaintHint()`, `docs/FEATURES.md` § J), and
`openIdeaModal()` calls it on every open, so it is never stale when it
matters and `applyUILang()` needs to know nothing about it. Everything
else in the modal — title, label, placeholder, both buttons — is plain
`data-i`/`data-i-placeholder`/`data-i-title` markup, which the generic
sweep handles.

**Four deliberate exceptions**, all of them permanently-visible surfaces
rather than modals — leaving one stale would show the previous language for
as long as it is open:

- `index.html`, the workbooks tree (`renderWorkbooks()`,
  `docs/FEATURES.md` § E);
- `index.html`, the knowledge graph's generated chrome
  (`gvRepaintLang()` — its legend, its group rows and its node/link count,
  § G);
- `index.html`, the search panel's generated chips, result blocks, chapter
  chevrons and count (`fdRepaintLang()`, § H) — the ⊟/⊞ button's title is
  set in `fdPaintOpts()` too, because it depends on the state, not only on
  the language;
- `index.html`, the importance pills in the preview — and these need **no
  exception at all**, which is the point worth copying: `renderImportance()`
  puts `data-i="impVital"` on the pill's label, and the preview is ordinary
  DOM, so `applyUILang()`'s generic `[data-i]` sweep re-translates it in
  place with no hook of its own. Emitting `data-i` from the parser is
  cheaper than a `*RepaintLang()` function whenever the generated content
  lives in the document rather than in a canvas or a rebuilt list. The
  export path passes `forExport` and emits the label with no `data-i`,
  because the exported page ships without the app (`docs/FEATURES.md` § C);
- `recipes.html`, the day cards, which also regenerate the markdown,
  because the markdown itself is written in the interface language (a
  Romanian UI writes `# Ziua 3`, an English one `# Day 3` — see
  `docs/RECIPES.md` § C). The reader that takes such a file back matches
  the `###` sections on their **leading digit** rather than on the word,
  precisely so a file written in one language opens in the other. The
  shareable HTML page (§ G there) is built with `t()` too, so it comes out
  in whatever language the interface is in — `<html lang>` included, and
  the nutrition tables' headings with it.

The 38 nutrients behind the detail panels are the **`nut_*` keys** — one
per nutrient key in `MICRO_DEFS`, looked up as `t("nut_" + key)`, so adding
a nutrient to that table means adding `nut_<key>` to both languages and
nothing else. Their five headings are `gCarb`, `gFat`, `gMin`, `gVit`,
`gOther`, plus `gMacro` for the four the panel repeats at the top. **Units
are not translated** — `g`, `mg`, `µg`, `kcal` are the same symbols in
both, and they live in `MICRO_DEFS` beside the key rather than in `I18N`.
`nHave` is a counted phrase and therefore a function of two numbers, and
it is one of the two that also has to cross into the exported page's
script: `docMicroTexts()` renders it with sentinel counts and swaps them
for `%a`/`%b`, exactly as `docFilterTexts()` does, so the plural rules of
both languages stay here.

One thing in `recipes.html` is deliberately **not** translated: the
`description` of a USDA food (`Oats, whole grain, rolled, old fashioned`).
It is the dataset's own text, it is what the `<datalist>` is searched by,
and it is how a row in the markdown says which food it means to a reader
who does not have this page — `docs/RECIPES.md` § E. The 62 local `L…`
rows are named in Romanian for the same reason: that is the language the
person adding one writes in.

Each is safe only because of two guards, and **a new call of this kind
needs both**: a `typeof … === "function"` test (all four are hoisted
`function` declarations, so it holds), and a boot flag — `wbBooted`,
`gvLangReady`, `fdReady` and `booted` respectively — each declared with
`var`, not `let`, so reading it early yields `undefined` instead of a
temporal-dead-zone crash. Anything reached from `applyUILang()` must
survive being called before the rest of the script has run.

## Porting checklist (per file) — reference, already done for all four

1. Extract strings → `I18N` object near the top of the app `<script>`.
   Start from these greps:
   ```bash
   grep -n "placeholder=\"\|title=\"\|aria-label=\"" editor.html
   grep -n "alert(\|confirm(\|prompt(" editor.html    # 5 here, 5 in markdown, 0 in index
   grep -n ">[A-Z][a-z].*<\/button>\|<label" editor.html
   ```
   Don't stop at markup — grep JS too (`textContent\s*=\s*['"\`]`,
   `innerHTML\s*=\s*['"\`]`) for dynamically-generated user-visible text
   (button state toggles, generated summaries, layer names, …).
2. Add `data-i` / `data-i-*` attributes to markup.
3. Add the language toggle to the **shared nav** so it appears in all
   apps identically (the nav is copied per file — see CLAUDE.md). Wire
   each app's own `applyUILang()`/storage to it via the
   `"scula-ui-lang"` event, per the wiring section above.
4. Run through the UI in both languages; check nothing overflows.

## Translation rules

- **Diacritics are mandatory:** ă â î ș ț. Use the proper comma-below
  characters `ș` (U+0219) / `ț` (U+021B), **not** the cedilla forms
  `ş`/`ţ` (U+015F/U+0163). They look nearly identical and break search.
  Verify with `/verify` (step 3 greps all four for the cedilla forms);
  `tests/recipes.js` also asserts it for `recipes.html` on both languages.
  **Text coming *in* is another matter** — a great many PDFs are set in the
  cedilla forms. `recipes.html` repairs them in `Recipes.clean()`, and its
  search folds them anyway; where such a character has to be named in code,
  write it as a `\u` escape so the file itself stays clean.
- Romanian runs **~15-25% longer** than English. `editor.html` is the tight
  one; three places to re-check after translating:
  - the top bar, which must stay **one row** on a desktop (it wraps, it
    never scrolls) — that's why `openImage`/`saveImage`/`saveAllSizes` are
    short labels with the full phrasing moved into `…Tip` keys;
  - the tool captions in `#toolsPanel`, ellipsised inside a 4-up grid — a
    label longer than ~11 characters will clip above 520px (below that the
    captions are hidden anyway);
  - `#selectionPanel` row labels (`.rlab`), which get a fixed ~5rem column
    in the `inline` rows.
- **Icons are not in the strings.** Buttons are
  `<span class="ticon">📂</span><span class="tlabel" data-i="…">`, so an
  i18n value is the label *only*. Don't reintroduce a leading emoji — it
  would show up twice.
- Keep keys semantic (`saveTooltip`), not literal (`btn3`).
- **Markdown syntax stays English in both languages.** `!nice` /
  `!important` / `!vital` and `Name>> ` are written into the file, and a
  file has to read the same whichever language it was written in — only the
  *label* on the rendered marker is translated (`impNice`/`impImportant`/
  `impVital`, plus the `imp*Opt` variants the toolbar select shows). Same
  rule for anything new that lands in the document rather than the chrome.
- One key per concept — don't reuse "Open" for a verb and a noun; RO
  needs different words. The reverse trap bit the graph: `linkBtn`
  ("🔗 Link", a URL) and `wikilinkBtn` (a link to a note) sit next to each
  other in the toolbar, and both wanted to be *Legătură* in Romanian. The
  second is named after what it points at — **⟦⟧ Notiță** — rather than
  after the act of linking.
- The knowledge-graph keys (`gv*`, `wiki*`, `wl*`, `scope*`, `graph*`)
  translate Obsidian's own vocabulary. Romanian settled on: *caiet* =
  workbook, *capitol* = chapter, *notiță* = note, *secțiune* = a heading
  inside one, *bloc* = a `^anchor`, *etichetă* = tag, *graf* = graph. Keep
  the app's existing caiet/capitol words for the workbook layer and use
  *notiță* only where Obsidian says "note"; mixing them reads as two
  different features.
- **A name that becomes a folder is not a translated string.** The
  `Idei` workbook the idea box falls back to (`IDEA_BOOK` in
  `index.html`, `docs/FEATURES.md` § J) stays `Idei` in both languages —
  it is a directory on disk and a chapter's home, and translating it per
  language would split one person's ideas across two folders. Same
  reasoning as the `!nice`/`!important`/`!vital` marker syntax staying
  English while only its pill label is translated (§ C there).
- `LilitaOne-Regular.ttf` **does not cover Romanian diacritics** (upstream
  limitation). `fontCss()` in `editor.html` appends a `sans-serif`
  fallback so glyphs degrade instead of showing tofu. Don't use Lilita One
  for UI chrome — every other bundled font (Poppins, Raleway, Roboto, Ink
  Free's fallback, Noto Mono, Excalifont, Nunito, Comic Shanns Mono) is
  verified to cover ă â î ș ț.
